## :book:&nbsp; Overview

This repository manages a bare-metal Kubernetes cluster running [Talos Linux](https://www.talos.dev/). Infrastructure is declared as code and deployed via [Flux CD](https://fluxcd.io/) GitOps. HTTP ingress uses [Envoy Gateway](https://gateway.envoyproxy.io/) with the [Kubernetes Gateway API](https://gateway-api.sigs.k8s.io/); some services also expose dedicated LoadBalancer IPs.

**Cluster Details** (verified 2026-09-29; desired versions are in [talconfig.yaml](kubernetes/bootstrap/talos/talconfig.yaml)):
- **OS**: Talos Linux v1.13.0
- **Kubernetes**: v1.36.0
- **Cluster Name**: `home-kubernetes`
- **API Endpoint**: `https://192.168.3.20:6443` (VIP shared across control plane nodes)
- **Pod CIDR**: `10.69.0.0/16`
- **Service CIDR**: `10.96.0.0/16`
- **CNI**: Cilium (Flannel disabled)

## GitOps with Flux CD

The cluster is managed entirely through GitOps using Flux CD. Changes are committed to this repository and automatically reconciled by Flux.

**Key Flux resources:**
- `flux-system` — Git source and entry-point Kustomization generated by the Flux instance
- `cluster-repositories` — Helm, Git, and OCI repository sources
- `cluster-apps` — All application workloads, with SOPS decryption for secrets

As verified on 2026-09-29, the Git source polls every minute and the `flux-system` entry point has a 10-minute interval. The two child root Kustomizations have 1-hour intervals; app intervals are commonly 30 minutes. New source revisions trigger reconciliation without waiting for those periodic intervals.

When committing, use `task flux:commit -- "<commit message>"`. It pulls, stages **all** changes, commits, pushes, and requests reconciliation of `flux-system` with its source. Review the working tree first and check Flux readiness afterward; a reconcile request does not guarantee every application is healthy.

Secrets are encrypted with [SOPS](https://github.com/getsops/sops) and decrypted at reconciliation time. Flux variable substitution is used for templating values like `${SECRET_DOMAIN}` and `${SECRET_DOMAIN_TWO}` across manifests.

## Safe Shutdown for a Power Outage

Use [scripts/shutdown-cluster.sh](scripts/shutdown-cluster.sh) for a planned full-cluster shutdown. It is specific to the five nodes and workload controllers in this repository. **By default it only performs a read-only preflight.** Execution requires `--execute` and typing `SHUTDOWN home-kubernetes`; there is no unattended confirmation bypass.

### Before Starting

- Run from your Mac on the LAN, not from a cluster pod or GitHub runner. Budget time for full CNPG backups as well as workload shutdown; the script allows up to one hour per final database backup. Keep the NAS, networking, and UPS running throughout cluster shutdown.
- Install `bash`, `jq`, `kubectl`, `talosctl`, and the `kubectl cnpg` plugin. Commands below run from the repository root. The script defaults to this repository's kubeconfig and generated Talos config; `KUBECONFIG` and `TALOSCONFIG` can override them.
- Verify recoverable application/database backups outside Ceph, preferably off-site. The script checks successful CNPG and configured VolSync backup timestamps within 36 hours and creates final CNPG backups after stopping application writers. It does not create other application backups, verify restores, or prove that every volume is covered. An etcd snapshot does not contain PVC data.
- Complete active Jobs, CNPG backups, and VolSync transfers. Stop external PostgreSQL writers before execution and keep them stopped through the final backups and shutdown; the script cannot fence external database clients. Stop external clients of Ceph NFS or other Ceph exports. Pause external deployment activity and avoid upgrades during the maintenance window.
- Investigate Ceph warnings first. The script requires all five OSDs up/in and every placement group exactly `active+clean`. Reviewed `HEALTH_WARN` conditions require `--allow-ceph-warnings`; missing OSDs, degraded PGs, or `HEALTH_ERR` cannot be bypassed.
- **Dragonfly currently has no configured persistent snapshots.** Stopping all replicas can lose sessions, queues, and other in-memory data. Export anything important and plan its restoration before proceeding. `--acknowledge-volatile-data-loss` explicitly accepts this risk; it does not back up or restore Dragonfly.
- Keep your Talos credentials, kubeconfig, SOPS Age key, backup credentials, and these instructions accessible offline. Verify how to power each node and the NAS back on; manually starting them is fine.

### Run the Shutdown

First review the live preflight and workload shutdown plan. This does not write recovery files or change the cluster:

```sh
bash scripts/shutdown-cluster.sh --dry-run
```

Choose a **new directory outside the repository** on your Mac. Its parent must already exist. The script records original replica counts, runner limits, schedule suspension states, CNPG hibernation, cluster identity, and Ceph flags, and downloads an etcd snapshot there before changing the cluster.

```sh
STATE_DIR="$HOME/cluster-shutdown-$(date +%Y%m%d-%H%M%S)"
bash scripts/shutdown-cluster.sh --execute --state-dir "$STATE_DIR"
```

The current Dragonfly configuration requires the explicit acknowledgment below. Add `--allow-ceph-warnings` only after investigating any warnings shown in the preflight:

```sh
bash scripts/shutdown-cluster.sh --execute --state-dir "$STATE_DIR" \
  --acknowledge-volatile-data-loss \
  --allow-ceph-warnings
```

If the operator has already validated recent Barman backups and explicitly accepts not taking final backups after writers stop, use `--use-existing-barman-backups` in both preflight and execution:

```sh
bash scripts/shutdown-cluster.sh --dry-run --use-existing-barman-backups
bash scripts/shutdown-cluster.sh --execute --state-dir "$STATE_DIR" \
  --use-existing-barman-backups --acknowledge-volatile-data-loss
```

This option records the latest completed Barman Backup resource within 36 hours for every active CNPG cluster. It does not run a new backup or restore test. It waives freshness checks only for those clusters' matching `<cluster>-logical-backup` VolSync sources; active transfers, unrelated VolSync sources, and all infrastructure checks still block shutdown when unhealthy. The selected backup resources are saved with the recovery state. These backups predate shutdown: recovery beyond them depends on retained WAL. Normal power-on still resumes the original PVCs, not a Barman restore.

The script performs these stages in order:

1. Check the expected node identities, readiness, direct Talos access, backup freshness, idle jobs, and Ceph health. Reject HPAs and StatefulSets configured to delete PVCs on scale-down.
2. Require confirmation, create private recovery files, and take a non-empty etcd snapshot. **The snapshot contains Kubernetes secrets.** Protect the directory with disk encryption and keep an encrypted recovery copy; never commit it.
3. Scale down the Flux operator and then Flux controllers so GitOps cannot undo maintenance changes. Flux resource suspension fields are left unchanged. Suspend CronJobs and CNPG ScheduledBackups, drain GitHub runner sets to zero, then stop upgrade, backup, and workload operators. Busy runners must finish within the wait timeout.
4. Stop applications and writers, then by default create a new CNPG `Backup` for each active cluster (`postgres16` and `postgres16vector`), with `method: barmanObjectStore` and `target: primary`. Wait for every new backup to reach `completed` before hibernating any PostgreSQL cluster. With `--use-existing-barman-backups`, use the selected existing backups instead. The CNPG operator, MinIO, network, and storage remain running during backups. Save each Backup resource, including its ID, server name, destination, timestamps, and WAL details when available, in `cnpg-backup-<namespace>-<cluster>.json` in the recovery directory. Then hibernate PostgreSQL, stop the other databases, and finally stop the CNPG operator, MinIO, and Kopia. Previously hibernated clusters stay untouched; original replicas, including zero, are recorded for recovery.
5. Refuse to proceed if PVC/NFS/inline CSI/ephemeral-volume consumers or VolumeAttachments remain. Keep CNI, DNS, CSI node plugins, and the API available while volumes unmount. Unknown or respawning storage consumers require manual investigation; the script does not force-delete pods or detach volumes.
6. Recheck Ceph, set `noout`, and stop Rook and the Ceph CSI controller before stopping CephFS/NFS services and CSI provisioners. Stop OSDs, then managers, then monitors. Wait for each stage's pods to disappear before continuing.
7. Submit Talos shutdown requests directly to each node: mars, jupiter, earth, venus, then mercury. `--force` skips Kubernetes cordon/drain only after workloads and storage have been stopped. `--wait=false` means request acceptance, **not confirmation that the machine is off**.

**Physically verify all five nodes are powered off.** Then shut down the NAS, followed by networking equipment and UPS outputs. Do not use the UPS to run the cluster until its battery dies. The script cannot power off external equipment or prevent it from restarting during electrical testing.

### Start Up and Restore

1. Wait for the electrician to confirm stable power. Start the UPS, modem/router/switch, and then the NAS. Verify DHCP, upstream DNS/time access, and NAS exports before proceeding.
2. Start all three control planes close together, then both workers. Do not wait for one control plane to become fully healthy before starting the others; etcd needs two of three members for quorum.
3. Use the **same recovery directory** from shutdown and type `RESTORE home-kubernetes` when prompted:

```sh
bash scripts/shutdown-cluster.sh --restore "$HOME/cluster-shutdown-YYYYMMDD-HHMMSS"
```

Restore verifies the saved cluster identity and node readiness. It restores recorded replicas in dependency order: Ceph monitors, managers/OSDs, remaining storage services and operators; then MinIO/Kopia, database services and CNPG, applications, other operators, runners and schedules, and finally Flux controllers and the Flux operator. Ceph must be fully peered and clean before applications are restored. A previously set `noout` flag or previously hibernated CNPG cluster is preserved; otherwise the script removes the maintenance flag and unhibernates PostgreSQL.

After databases start, restore pauses for `START-APPLICATIONS home-kubernetes`. Verify data and import any separately exported Dragonfly data in another terminal before confirming. The script does not perform that import. After a full shutdown, application writers and schedules remain stopped during this pause; recovery from a partial shutdown does not stop any applications that never stopped originally.

Check the recovered cluster and actual application access:

```sh
kubectl get nodes
kubectl -n rook-ceph exec deploy/rook-ceph-tools -- ceph status
kubectl get clusters.postgresql.cnpg.io -A
flux get kustomizations -A
flux get helmreleases -A
```

Verify internal and external routes, important application data, and the next successful backups.

### CNPG Persistence and Backup Recovery

Both CNPG clusters use `openebs-hostpath`. Their existing PVs store data under `/var/openebs/local/` on node disks and are pinned to their respective nodes. A clean shutdown and restart preserves those files; this is not temporary pod storage. CNPG hibernation retains the PVCs, and unhibernation resumes the existing databases rather than running bootstrap recovery. Bring the original nodes and disks back online. **The current PV reclaim policy is `Delete`: do not delete PVCs, wipe disks, or reset/reinstall Talos as part of this maintenance.** Local storage does not itself replicate data across nodes; CNPG manages PostgreSQL replication between its instances.

For an additional daily logical-backup policy without database downtime, see the opt-in [CNPG dump-to-VolSync manifests and restore runbook](kubernetes/apps/database/cloudnative-pg/logical-backups/README.md). These create separate staging PVCs; they do not copy live PostgreSQL data directories or replace Barman/WAL backups.

The final backups use each live Cluster's current backup configuration, not its older `bootstrap.recovery.source`:

| Cluster manifest | Current backup server name | Destination |
|---|---|---|
| [postgres16](kubernetes/apps/database/cloudnative-pg/cluster/cluster16.yaml) | `postgres16-v4` | `s3://cloudnative-pg/` via NAS-backed MinIO |
| [postgres16vector](kubernetes/apps/database/cloudnative-pg/cluster3/cluster16vector.yaml) | `postgres16vector-v4` | `s3://sensei-cnpg/` on AWS S3 |

If an actual rebuild from backup is necessary, the previous recovery pattern is to point `bootstrap.recovery.source` at the server name containing the final successful backup and choose a new, unused backup server name. With the current configuration, that means `source: &previousCluster postgres16-v4` and `serverName: &currentCluster postgres16-v5`; for the vector cluster, use `source: &previousCluster postgres16vector-v4` and `serverName: &currentCluster postgres16vector-v5`. The existing `externalClusters` aliases select the same previous server name. Verify the actual values and successful backup ID in the saved Backup resources before choosing a recovery source; do not blindly increment names if configuration has changed.

These changes are for a deliberate recovery into a new cluster/data directory, not a routine power-cycle. Changing bootstrap fields on an existing Cluster does not restore its data. The shutdown/restore script does not change server names, recreate CNPG clusters, or delete volumes. A rebuild requires a separately reviewed recovery plan with writers and Flux kept stopped and backup/WAL availability verified. Do not resume applications until the recovered data is checked.

### If a Step Fails

The script stops on errors or timed-out waits (10 minutes per workload wait, one hour per final CNPG backup) and does **not** automatically undo changes. A failed backup can keep the completion wait pending until its timeout; failure or timeout blocks CNPG hibernation and all subsequent storage/node shutdown. Inspect the saved `cnpg-backup-*.json` files and the live Backup status. Keep power on and inspect its output and `progress.log` in the recovery directory. A partially completed shutdown may leave workloads stopped and Flux disabled; this is intentional.

Do not rerun `--execute` over a partial shutdown: a new snapshot of already-scaled-down replicas is not the original recovery state. Resolve the blocker and use `--restore` with the original directory to return to service before attempting another shutdown. After any node has powered off, start all nodes and dependencies before restoration. If restoration stops while Ceph is recovering, inspect Ceph and rerun `--restore` with the same directory after recovery; completed restoration stages can be repeated.

Do not reset/re-bootstrap Talos, remove etcd members, delete PVCs, or tear down the Ceph cluster for a power outage. The recovery snapshot is for disaster recovery, not part of an ordinary restart.

### Validate Script Changes

The mocked regression tests never call real Kubernetes or Talos commands:

```sh
bash scripts/test-shutdown-cluster.sh
shellcheck -x scripts/shutdown-cluster.sh scripts/test-shutdown-cluster.sh
```

Re-run the read-only preflight when workloads, operators, storage, or node inventory change. Do not use `--execute` as a test.

### 1. Cloudflared Tunnel

Provides a secure tunnel from Cloudflare's edge network to the cluster, eliminating the need for direct port forwarding.

- Runs as a deployment in the `network` namespace
- Uses Cloudflare Tunnel ID to establish a secure connection
- Routes traffic based on hostname to Envoy Gateway
- Uses HTTP/2 origin connections

**Tunnel routing** ([config.yaml](kubernetes/apps/network/cloudflared/app/configs/config.yaml)):
```yaml
originRequest:
  http2Origin: true
  noHappyEyeballs: false
ingress:
  - hostname: "${SECRET_DOMAIN}"
    service: https://envoy-external.network.svc.cluster.local:443
    originRequest:
      originServerName: "external.${SECRET_DOMAIN}"
  - hostname: "*.${SECRET_DOMAIN}"
    service: https://envoy-external.network.svc.cluster.local:443
    originRequest:
      originServerName: "external.${SECRET_DOMAIN}"
  - hostname: "${SECRET_DOMAIN_TWO}"
    service: https://envoy-external.network.svc.cluster.local:443
    originRequest:
      originServerName: "external.${SECRET_DOMAIN_TWO}"
  - hostname: "*.${SECRET_DOMAIN_TWO}"
    service: https://envoy-external.network.svc.cluster.local:443
    originRequest:
      originServerName: "external.${SECRET_DOMAIN_TWO}"
  - hostname: "${SECRET_DOMAIN_THREE}"
    service: https://envoy-external.network.svc.cluster.local:443
    originRequest:
      originServerName: "external.${SECRET_DOMAIN_THREE}"
  - hostname: "*.${SECRET_DOMAIN_THREE}"
    service: https://envoy-external.network.svc.cluster.local:443
    originRequest:
      originServerName: "external.${SECRET_DOMAIN_THREE}"
  - service: http_status:404
```

**DNS Endpoints** ([dnsendpoint.yaml](kubernetes/apps/network/cloudflared/app/dnsendpoint.yaml)):
- `external.${SECRET_DOMAIN}` → `${SECRET_CLOUDFLARE_TUNNEL_ID}.cfargotunnel.com`
- `external.${SECRET_DOMAIN_TWO}` → `${SECRET_CLOUDFLARE_TUNNEL_ID}.cfargotunnel.com`
- `external.${SECRET_DOMAIN_THREE}` → `${SECRET_CLOUDFLARE_TUNNEL_ID}.cfargotunnel.com`
- `external-gateway.${SECRET_DOMAIN}` → `${SECRET_CLOUDFLARE_TUNNEL_ID}.cfargotunnel.com`

### 2. Envoy Gateway

Handles all ingress traffic using the Kubernetes Gateway API. Two separate Gateways serve different network zones.

**Deployment details:**
- Helm chart: `oci://mirror.gcr.io/envoyproxy/gateway-helm` (via OCIRepository)
- 2 replicas per gateway for high availability
- EnvoyPatchPolicy enabled for advanced configuration
- GatewayClass: `envoy`

#### External Gateway (`envoy-external`)

Handles internet-facing services accessible via the Cloudflare tunnel.

- LoadBalancer IP: `192.168.3.26`
- Listeners: HTTP (port 80), HTTPS (port 443)
- HTTPS listener allows routes from all namespaces
- HTTP listener restricted to `network` and `database` namespaces (for redirects)
- Automatic HTTP → HTTPS redirect (301)

#### Internal Gateway (`envoy-internal`)

Handles services accessible only on the local network.

- LoadBalancer IP: `192.168.3.27`
- Listeners: HTTP (port 80), HTTPS (port 443)
- HTTPS listener allows routes from all namespaces
- HTTP listener restricted to same namespace (for redirects)
- Automatic HTTP → HTTPS redirect (301)

#### Traffic Policies

**BackendTrafficPolicy:**
- Compression: Zstd, Brotli, Gzip
- Connection buffer limit: 8Mi
- TCP keepalive enabled
- No request timeout (unlimited)

**ClientTrafficPolicy:**
- Client IP detection via X-Forwarded-For (1 trusted hop)
- Connection buffer: 8Mi
- HTTP/2: 2Mi stream window, 32Mi connection window, 100 max concurrent streams
- HTTP/3 enabled
- TLS minimum version: 1.2
- ALPN protocols: h2, http/1.1

**EnvoyPatchPolicy:**
- Zstd compression on both gateways via filter chain patches
- Lua filter on external gateway to extract X-Real-IP from X-Forwarded-For

### 3. External-DNS

Automatically manages DNS records in Cloudflare based on Kubernetes resources.

- Watches Gateway HTTPRoute resources (via `--gateway-name=envoy-external`)
- Watches DNSEndpoint custom resources
- Creates Cloudflare-proxied DNS records
- TXT ownership records are prefixed with `k8s.`; service hostnames are not
- Manages domains: `${SECRET_DOMAIN}`, `${SECRET_DOMAIN_TWO}`, and `${SECRET_DOMAIN_THREE}`
- Sources: `crd`, `ingress`, `gateway-httproute`

### 4. K8s-Gateway

Provides local DNS resolution so devices on the LAN can access cluster services without routing through the internet.

- DNS server on port 53
- LoadBalancer IP: `192.168.3.22`
- Watches Ingress, Service, and HTTPRoute resources
- Returns gateway LoadBalancer IPs for hostname queries
- Domains: `${SECRET_DOMAIN}`, `${SECRET_DOMAIN_TWO}`, and `${SECRET_DOMAIN_THREE}`
- TTL: 1 second

**Usage**: Configure your local DNS server (router, Pi-hole, etc.) to forward queries for `${SECRET_DOMAIN}`, `${SECRET_DOMAIN_TWO}`, and `${SECRET_DOMAIN_THREE}` to `192.168.3.22`.

### 5. Cert-Manager

Manages TLS certificates from Let's Encrypt using DNS-01 challenge validation with Cloudflare.

**Cluster Issuers:**
- `letsencrypt-production` — Production certificates
- `letsencrypt-staging` — Testing certificates

**Wildcard Certificates** ([kubernetes/apps/network/envoy-gateway/certificates/production.yaml](kubernetes/apps/network/envoy-gateway/certificates/production.yaml)):

| Certificate | Secret | Covers |
|-------------|--------|--------|
| `${SECRET_DOMAIN/./-}-production` | `${SECRET_DOMAIN/./-}-production-tls` | `${SECRET_DOMAIN}`, `*.${SECRET_DOMAIN}` |
| `${SECRET_DOMAIN_TWO/./-}-production` | `${SECRET_DOMAIN_TWO/./-}-production-tls` | `${SECRET_DOMAIN_TWO}`, `*.${SECRET_DOMAIN_TWO}` |
| `${SECRET_DOMAIN_THREE/./-}-production` | `${SECRET_DOMAIN_THREE/./-}-production-tls` | `${SECRET_DOMAIN_THREE}`, `*.${SECRET_DOMAIN_THREE}` |

Both Envoy Gateways reference these certificate secrets for TLS termination. No per-service certificate configuration is needed for one-level subdomains of these domains.

## Network Traffic Flows

### External Traffic (Internet → Service)

```
Internet User
    ↓
Cloudflare Edge Network (DNS + proxy)
    ↓
Cloudflared Tunnel (in cluster)
    ↓
Envoy External Gateway (192.168.3.26)
    ↓
HTTPRoute → Service Pod
```

**Step-by-step:**
1. User requests `https://app.${SECRET_DOMAIN}`
2. DNS resolves to Cloudflare (via External-DNS managed CNAME)
3. Cloudflare proxies the request through the tunnel to the cloudflared pod
4. Cloudflared forwards to `envoy-external.network.svc.cluster.local:443`
5. Envoy matches the HTTPRoute by hostname and routes to the backend service
6. TLS is terminated at the Gateway using the wildcard certificate

### Internal Traffic (Local Network → Service)

```
Local Device
    ↓
K8s-Gateway DNS (192.168.3.22)
    ↓ (returns 192.168.3.27)
Envoy Internal Gateway (192.168.3.27)
    ↓
HTTPRoute → Service Pod
```

**Step-by-step:**
1. Local device queries `app.${SECRET_DOMAIN}`
2. Local DNS server forwards to K8s-Gateway (`192.168.3.22`)
3. K8s-Gateway returns `192.168.3.27` (internal gateway IP)
4. Device connects directly to the Envoy Internal Gateway
5. Envoy matches the HTTPRoute by hostname and routes to the backend service

## Deploying New Services

Services are exposed using HTTPRoute resources from the Kubernetes Gateway API.

### External Service (Internet-Accessible)

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: myapp
  namespace: myapp
  annotations:
    external-dns.alpha.kubernetes.io/cloudflare-proxied: "true"
spec:
  parentRefs:
    - name: envoy-external
      namespace: network
      sectionName: https
  hostnames:
    - myapp.${SECRET_DOMAIN}
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: myapp
          port: 80
```

**What happens:**
1. External-DNS detects the HTTPRoute attached to `envoy-external`
2. Creates a Cloudflare-proxied CNAME: `myapp.${SECRET_DOMAIN}` → `external.${SECRET_DOMAIN}`
3. `external.${SECRET_DOMAIN}` → Cloudflare Tunnel (via DNSEndpoint)
4. Cloudflared forwards traffic to Envoy External Gateway
5. Envoy routes to the backend service
6. TLS is handled by the gateway's wildcard certificate

### Internal Service (Local Network Only)

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: myapp
  namespace: myapp
  annotations:
    external-dns.alpha.kubernetes.io/exclude: "true"
spec:
  parentRefs:
    - name: envoy-internal
      namespace: network
      sectionName: https
  hostnames:
    - myapp.${SECRET_DOMAIN}
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: myapp
          port: 80
```

**What happens:**
1. K8s-Gateway detects the HTTPRoute
2. Returns `192.168.3.27` (internal gateway IP) for DNS queries
3. Local devices connect directly to Envoy Internal Gateway
4. Envoy routes to the backend service
5. TLS is handled by the gateway's wildcard certificate

### Dual-Mode Service (Both Internal and External)

Create two separate HTTPRoute resources pointing to the same backend:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: myapp-external
  namespace: myapp
  annotations:
    external-dns.alpha.kubernetes.io/cloudflare-proxied: "true"
spec:
  parentRefs:
    - name: envoy-external
      namespace: network
      sectionName: https
  hostnames:
    - myapp-public.${SECRET_DOMAIN}
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: myapp
          port: 80
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: myapp-internal
  namespace: myapp
  annotations:
    external-dns.alpha.kubernetes.io/exclude: "true"
spec:
  parentRefs:
    - name: envoy-internal
      namespace: network
      sectionName: https
  hostnames:
    - myapp.${SECRET_DOMAIN}
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: myapp
          port: 80
```

### Advanced HTTPRoute Features

**Path-based routing with URL rewrites:**
```yaml
rules:
  - matches:
      - path:
          type: PathPrefix
          value: /v1
    filters:
      - type: URLRewrite
        urlRewrite:
          path:
            type: ReplacePrefixMatch
            replacePrefixMatch: /
    backendRefs:
      - name: myapp-v1
        port: 8080
  - matches:
      - path:
          type: PathPrefix
          value: /v2
    backendRefs:
      - name: myapp-v2
        port: 8080
```

**Header-based routing:**
```yaml
rules:
  - matches:
      - headers:
          - name: X-Version
            value: beta
    backendRefs:
      - name: myapp-beta
        port: 8080
  - backendRefs:
      - name: myapp-stable
        port: 8080
```

**Traffic splitting (canary deployments):**
```yaml
rules:
  - backendRefs:
      - name: myapp-v2
        port: 8080
        weight: 10
      - name: myapp-v1
        port: 8080
        weight: 90
```

## Certificate Management

### Default Wildcard Certificates

Both Envoy Gateways are configured with certificates for `${SECRET_DOMAIN}`, `${SECRET_DOMAIN_TWO}`, and `${SECRET_DOMAIN_THREE}`, including one-level wildcard subdomains of each. Routes attached to their HTTPS listeners use these certificates without per-service TLS configuration.

### Custom Certificates

For domains outside the wildcard coverage:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: myapp-custom-cert
  namespace: myapp
spec:
  secretName: myapp-custom-tls
  issuerRef:
    name: letsencrypt-production
    kind: ClusterIssuer
  dnsNames:
    - myapp.example.com
```

Then reference the secret in a Gateway listener or use [ReferenceGrant](https://gateway-api.sigs.k8s.io/api-types/referencegrant/) to allow cross-namespace secret access.

For a new externally served domain, also update the Cloudflared ingress rules and External-DNS domain filters; update K8s-Gateway's domains and LAN DNS forwarding when internal resolution is needed. A new certificate alone does not configure routing or DNS.

## Troubleshooting

### Service not accessible from the internet

1. Verify the HTTPRoute is attached to `envoy-external`:
   ```bash
   kubectl get httproute -n <namespace> <name> -o yaml | grep -A5 parentRefs
   ```

2. Check HTTPRoute status (accepted by gateway):
   ```bash
   kubectl describe httproute <name> -n <namespace>
   ```

3. Verify External-DNS created the DNS record:
   ```bash
   kubectl logs -n network -l app.kubernetes.io/name=external-dns --tail=50
   ```

4. Check Cloudflared tunnel is running:
   ```bash
   kubectl get pods -n network -l app.kubernetes.io/name=cloudflared
   kubectl logs -n network -l app.kubernetes.io/name=cloudflared --tail=50
   ```

5. Check Envoy Gateway proxy logs:
   ```bash
   kubectl logs -n network -l gateway.envoyproxy.io/owning-gateway-name=envoy-external --tail=50
   ```

### Service not accessible from local network

1. Verify the HTTPRoute is attached to `envoy-internal`:
   ```bash
   kubectl get httproute -n <namespace> <name> -o yaml | grep -A5 parentRefs
   ```

2. Verify K8s-Gateway is running:
   ```bash
   kubectl get pods -n network -l app.kubernetes.io/name=k8s-gateway
   ```

3. Test DNS resolution:
   ```bash
   dig @192.168.3.22 myapp.${SECRET_DOMAIN}
   # Should return 192.168.3.27
   ```

4. Ensure your local DNS forwards to K8s-Gateway:
  - Router or Pi-hole should forward `${SECRET_DOMAIN}`, `${SECRET_DOMAIN_TWO}`, and `${SECRET_DOMAIN_THREE}` to `192.168.3.22`

### Certificate issues

1. Check certificate status:
   ```bash
   kubectl get certificate -A
   ```

2. Check Cert-Manager logs:
   ```bash
   kubectl logs -n cert-manager -l app.kubernetes.io/name=cert-manager
   ```

3. Verify ClusterIssuers are ready:
   ```bash
   kubectl get clusterissuer
   ```

### Gateway issues

1. Check Gateway status:
   ```bash
   kubectl get gateway -n network
   kubectl describe gateway envoy-external -n network
   kubectl describe gateway envoy-internal -n network
   ```

2. Check Envoy Gateway controller logs:
   ```bash
   kubectl logs -n network -l app.kubernetes.io/name=envoy-gateway --tail=50
   ```

## Best Practices

1. **Gateway Selection**:
   - Use `envoy-external` only for services that need internet access
   - Default to `envoy-internal` for security-sensitive services
   - Never expose admin panels externally unless protected by authentication (e.g., Authelia)

2. **DNS Naming**:
   - Use descriptive subdomains: `app.${SECRET_DOMAIN}` not `app1.${SECRET_DOMAIN}`
   - Keep external and internal subdomains separate for dual-mode services

3. **HTTPRoute Annotations**:
   - Add `external-dns.alpha.kubernetes.io/exclude: "true"` for internal-only services
   - Add `external-dns.alpha.kubernetes.io/cloudflare-proxied: "true"` for external services

4. **TLS**:
   - Let the gateway's wildcard certificates handle TLS automatically
   - Only create custom certificates for domains outside wildcard coverage

5. **Namespaces**:
   - Keep related services in the same namespace
   - HTTPRoutes should live in the same namespace as their backend services
